- *Building a virtual research environment (almost) from scratch for the Heritage Science Data Service* (RSECon26 talk, 11 Sept 2026; `raw/Building a virtual research environment (almost) from scratch for the Heritage Science Data Service.md`, [Zenodo record 22145961](https://zenodo.org/records/22145961), `raw/HSDS-RSECon26.pdf`; Dan Clayton, Ayman Izzeldin, Simona Graur, Dylan Bennett, Mohammed Hashim, and Dave Meredith, STFC Hartree Centre): The Heritage Science Data Service (HSDS) — a partnership between the Archaeology Data Service and STFC Hartree Centre serving heritage-science workloads (3D scanning, X-ray/CT/XRF imaging, lidar/geophysics remote sensing, GIS) across a consortium including the National Gallery, National Archives, British Geological Survey, British Museum, Historic England/Environment Scotland, and others, funded by a £15.3M AHRC investment under the 2024-2029 RICHeS programme. Motivates a browser-based Virtual Research Environment (VRE) from exploding data scale (HS2 alone has generated 34Tb of heritage data) and GPU-hungry, specialist-software workflows that don't run on corporate laptops. Rejected off-the-shelf options (Kasm and cloud-vendor equivalents) for a custom build on open-source components, since scheduling, file management, project collaboration, and HSDS-Data-Catalogue integration all needed bespoke logic anyway. Frames the whole build as a "user needs shaped the architecture" case study transferable to other RSEs building bespoke research infrastructure, even where it means learning tools (like Active Directory) outside their normal skillset. - *PyEarthTools: Accelerating the use of machine learning for reproducible environmental science* (RSECon26 talk, 11 Sept 2026; `raw/PyEarthTools_ Accelerating the use of machine learning for reproducible environmental science.md`, [Zenodo record 22206460](https://zenodo.org/records/22206460), `raw/20260911_RSE_walkthrough_PyEarthTools_Intro.pdf`; Stephen Haddad, Data Science Lead, Met Office): A Python framework addressing why environmental-science ML pipelines don't work "out of the box" — bespoke platform/dataset-specific code, non-FAIR data and tooling, data that isn't ML-ready, and an ecosystem of tools that doesn't support rapid ML development. Positioned against both bespoke code and generic ML tooling (MLFlow, Hugging Face, Intake, STAC) and against other weather/climate-specific ML frameworks (ECMWF's Anemoi, EUMetNet's MLCast, NCAR's CREDIT), built around four motivations: traceability, accessibility, reproducibility, and community building. Originated in 2022 at the Australian Bureau of Meteorology (before any comparable public framework existed), joined mid-2024 by the Met Office (UK) and ACCESS-NRI (Australia), released open-source Dec 2024, with 2025-2026 work on tutorials, a Momentum Partnership hackathon, a user forum, and nowcasting development. Architecture: an ecosystem of Python packages (Data, Utils, Pipeline, Training, Tutorial, Bundled Models, Zoo) built around four core concepts — Data Accessors, Data Operators, Data Pipelines, and a Model Zoo — where a pipeline is a directed graph chaining named operators (region bounding, temporal retrieval, normalisation, format conversion) over named data sources (ERA5, Himawari, ACCESS Analysis), independent of ML architecture and runnable across laptops, workstations, and supercomputers. A working example of "publish and share pipelines" as the reproducibility mechanism, not just disclosure. Keywords: PyEarthTools, environmental science, machine learning weather prediction, FAIR pipelines, Met Office, xarray. Related: [[Machine_Learning]], [[Climate_Change]], [[Remote_Sensing]].

- *PEtab SciML: a format specification for solving parameter estimation problems using scientific machine learning in computational biology and beyond* (RSECon26 talk, 11 Sept 2026; three captured sources — `raw/PEtab SciML_ a format specification for solving parameter estimation problems using scientific machine learning in computational biology and beyond.md` ([Zenodo record 22141642](https://zenodo.org/records/22141642)), `raw/PEtab SciML.md` (the full reveal.js slide deck, bsnelling.github.io), and `raw/File (5).md` (Oxford Abstracts abstract) — Branwen Snelling, Sebastian Persson, and Fabian Fröhlich, The Francis Crick Institute, with contributions from Maren Philipps and Dilan Pathirana, University of Bonn): Extends PEtab (an existing tabular TSV/YAML format for parameter-estimation problems in systems biology) to scientific machine learning — hybrid models where mechanistic ODEs (reaction rates, binding affinities, degradation constants that are unknown/unmeasurable) are augmented with neural-network components to capture dynamics that are hard to write down mechanistically. Supports four hybridisation patterns: learning dynamic terms within the ODE, mapping high-dimensional inputs (e.g. images) upstream to model parameters, learning the observable formula linking model outputs to real measurements, and full Neural ODEs replacing the ODE's right-hand side. A worked example walks an epidemiological SIR-plus-quarantine model where a neural network learns the time-varying, policy-dependent quarantine-strength term directly from Dandekar et al.'s (*Patterns*, 2020) case data — a Universal Differential Equation (UDE) — implemented as an Antimony-authored SBML model, a hybridisation table mapping network inputs/outputs to model terms, an ecosystem-agnostic YAML network-architecture spec (usable to build either a PyTorch or Lux module), and HDF5 array files for parameters/inputs; trained via AMICI's JAX-based differentiable-simulation import in Python (or PEtab.jl in Julia). Its reproducibility case echoes the rest of this page: a hybrid problem fully defined by a standard set of files rather than bespoke code, importable across ecosystems, with a transferable ML-model format reducing per-system reimplementation. Keywords: PEtab SciML, scientific machine learning, Universal Differential Equation, hybrid modelling, computational biology, format specification. Related: [[Machine_Learning]].

- *Cui & Alexander (2026), "Same Prompt, Different Outcomes: Evaluating the Reproducibility of Data Analysis by LLMs"* (`raw/2602.14349v1.pdf`, [arXiv:2602.14349](https://arxiv.org/abs/2602.14349), 15 Feb 2026): A systematic evaluation of whether LLM-generated data analysis reproduces consistently. The authors run 480 total execution attempts — six models across three providers (Claude Haiku 4.5 and Claude Opus 4.6, GPT-5-mini and GPT-5.2, Gemini Flash 3 and Gemini Pro 3), four temperature settings (0.0, 0.3, 0.7, 1.0), two prompting strategies (single-step vs. multi-step with intermediate validation), and ten independent executions per configuration — on a realistic five-step pipeline (consolidating government-appointment records for a Canadian province, identifying reappointment patterns, aggregating to analytical units, running an OLS regression, and producing visualizations), scored on completion, concordance with a human-conducted analysis, output validity, and cross-run consistency. Three main findings: single-step prompting has higher completion rates than multi-step, because in multi-step pipelines an error at any stage blocks all later stages (e.g. Gemini Flash 3 hits 100% completion single-step but 0% multi-step, failing every run at Step 2 on file-path handling); generated code is almost always structurally valid but diverges from the human analysis in underspecified data-preparation choices (sorting, missing-value handling, record inclusion); and these data-preparation differences propagate into the analysis, producing distinct clusters of estimated regression slopes that vary in both sign and magnitude — meaning identical prompts, data, and even temperature-zero settings can support different substantive conclusions. The paper's own AI-usage statement discloses that AI assisted with coding, data cleaning, and figure/table generation, with all code and results reviewed by the human authors. Cited by Nicolas Rougier in the GFRN consultation input above as motivating a requirement to disclose prompts when they substantially determine the result. Keywords: LLM reproducibility, data analysis, many-analysts, non-determinism, prompt engineering, AI disclosure. Related: [[Machine_Learning]], [[Professional_Background]].

- *Beyond FAIR Data: Making Research Software a First-Class Research Output* (`raw/2026-06-11-SNS-EELISA.pdf`): A 59-slide course/talk by Roberto Di Cosmo (Director, Software Heritage; Inria/Université Paris Cité), delivered 11 June 2026 — the filename suggests it was given for the EELISA European university alliance. Builds on a Nature commentary (Oct 2025, doi:10.1038/d41586-025-03196-0) calling for software to get the same archive/reference/citation/credit treatment as data, and frames the whole talk as "the how-to behind that call." Opens from Popper's reproducibility principle to argue that preserving source code itself — not just describing methods — is what makes computational research verifiable. Core technical content: the SWHID (Software Hash Identifier), an intrinsic, content-derived identifier built from a Merkle DAG of a project's full development history, which anyone can recompute offline to verify an archived copy matches the original ("a DOI answers 'which deposit?'; a SWHID answers 'exactly which bytes, and prove it'"); practical tooling for researchers — the CodeMeta Generator and an auto-derived `CITATION.cff` for describing software, and the HAL/Software Heritage curated-deposit workflow used in French research; adoption evidence, including a Spinellis et al. MSR 2026 dataset citing 30 SWHIDs and a population-genetics paper embedding SWHIDs since 2020. Closes on policy stakes: the 2019 EU Copyright Directive's "upload filter" rules, where Software Heritage helped secure a non-profit-archive exclusion, and the 2021 US Executive Order's software-supply-chain-security ("Know Your SoftWare") provisions — plus an infrastructure timeline from the archive's 2015 launch through its 2026 ENEA institutional mirror. Keywords: SWHID, CodeMeta, FAIR software, research software citation, Merkle DAG, software supply chain. Related: [[Professional_Background]], [[Data]].
