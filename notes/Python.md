- ["Demystifying the Django ORM" with Simon Charette](https://www.youtube.com/watch?v=IakfTkQIuFw) (Djangonaut Space, recorded for the 2024 Session 3 cohort, published 18 Nov 2024, 44 min; [slides](http://charettes.name/djangonauts2024/), 26 pages): Simon Charette, a Django contributor for about ten years who works mostly on the ORM and migrations, explains how a QuerySet becomes SQL and comes back as model instances, in four phases. (i) **Resolving**: lazy and cumulative; each `filter()` or `annotate()` builds nested "resolvable" objects (most are `Expression` subclasses) on a `sql.Query`, with no database-specific logic. (ii) **Compilation**: triggered by the first non-lazy operation; the router picks the `DATABASES` entry, an operation-specific compiler (`SQLCompiler`, `SQLInsertCompiler`, `SQLUpdateCompiler`, `SQLDeleteCompiler`) calls `as_sql()` recursively and returns `(sql, params)`. (iii) **Execution**: the SQL and parameters go through the PEP 249 driver (for example psycopg) and come back as a list of tuples or an exception. (iv) **Construction**: values are coerced with `Field.from_db_value`, then returned as dicts (`values()`), tuples (`values_list()`) or model instances. The Q&A covers `get_or_create` (use it rather than writing your own, because of race conditions), what `F()` is, what lazy means, what he would change if compatibility could break (some resolving still reads the default connection's features, which blocks a fully async ORM), and a working tip: use `git blame` on a line to walk back to its pull request and ticket. Watched as preparation for the ORM track of Djangonaut Space Session 7. Keywords: Django ORM, QuerySet, SQL compilation, expressions, lazy evaluation, Djangonaut Space. Related: [[SQL]], [[Open_Source]].

- [Time complexity of operations on built-in types](https://docs.python.org/3/builtins/time-complexity.html) (Python 3 documentation): The official CPython Big-O reference for `list`, `tuple`, `dict`, `set`/`frozenset`, `str`/`bytes`/`bytearray`, `memoryview`, and `range`. Key points: list append/index/length are *O*(1) but insert/delete near the front are *O*(n) since everything after must shift (use `collections.deque` for both-end queues); dict/set operations are *O*(1) average-case (assuming well-distributed hashes) but degrade to *O*(n) worst-case under hash collisions; `bytearray` supports amortized *O*(1) front-deletion by advancing the buffer start rather than moving bytes; `range` objects compute items on demand so most operations (including slicing) are *O*(1) regardless of range length. Keywords: Python, Big O notation, time complexity, CPython, data structures, algorithmic complexity.
